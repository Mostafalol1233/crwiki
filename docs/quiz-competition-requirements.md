# CrossFire Wiki Competition and Admin Reliability Requirements

_Source: `quizofcrossfirewiki.rar/prompt.md`, extracted on 2026-08-21._

## Existing reliability fixes requested

The supplied prompt reports schema or row-level security failures when creating or editing Highlights. It also reports that the admin user page does not show available administrators and does not allow creating an administrator with scoped access. The announcements system is expected to remain data-driven: existing announcements must be retrievable and active announcements must render publicly rather than relying on a hard-coded placeholder.

These reliability issues should be addressed before launching the competition feature. Administrative writes must use the existing authenticated server-side administration path, preserve RLS protection, return actionable errors, and avoid adding another Vercel function because the project is already at its serverless-function limit.

## Competition experience

Create a bilingual public competition page in English and Arabic. The page should introduce a CrossFire Wiki competition organized by CrossFire Wiki and its named contributors or supporters: Zenith Clan, Antifarming Clan, Diaasadek as a top-up seller, and Bemora as the creator. The public page should explain the rules, joining-code requirement, question formats, scoring, leaderboard, and prize categories in plain language.

Participants must sign in with the website’s existing authentication flow and enter an invitation code generated by an administrator. The participant should be asked for a phone number as part of registration, with clear consent and an explanation that the number is used for competition contact. The code should not be exposed in public UI or hard-coded in the client.

## Scoring and proof rules

The core assessment is a multiple-choice quiz. Subscription or community participation proofs are optional score bonuses rather than a strict prerequisite: a participant may take the exam without them, but verified proofs can raise the final score. Proofs may include an image showing subscription to a contributor or community channel and a purchase receipt from the named seller. A newer purchase receives a higher bonus than an older purchase, but the exact point values must be configurable by an administrator rather than invented in the frontend.

Participants should be able to upload proof images after submitting the exam. Upload validation must restrict file type and size, store files through the project’s configured storage path, and associate each proof with the participant and competition attempt. The public result screen should explain that a participant can still improve the competition score by submitting eligible proofs.

## Question bank

The initial quiz should contain approximately 25 questions, with an administrator-managed question bank. The first version should include:

1. Audio identification questions using the supplied CrossFire MP3 files. Each question should play a controlled audio clip and provide difficult but fair choices for the related map or mode. The answer labels must be verified against the audio filename and game context; filenames alone should not be treated as perfect evidence for ambiguous clips.
2. Weapon-choice questions based on individual West-version weapons already present in the project’s database. Avoid the newest or unreleased items and avoid weapons that belong only to other regional versions. The question bank should reference weapon records rather than duplicating names in code.
3. Two or three scenario or essay questions. Examples in the prompt involve Desert Eagle with a weak but cooperative team against a 3A/2B enemy split, and Ship TDM against a very strong opponent who appears suspicious. These should be reviewed for fair, non-accusatory wording and scored through an administrator review workflow rather than automated claims about cheating.

Question order, answer options, correct answers, point values, audio references, language text, publication status, and accepted essay review status must be editable by administrators. The initial set must not include invented answer keys; ambiguous items should be marked draft until reviewed.

## Results, leaderboard, and prizes

After submission, participants should see their objective score and a clear message that eligible proofs may add bonus points. The leaderboard should use a deterministic score and tie-break policy configured by the administrator. The prompt names prize categories but does not provide final quantities or ranking allocations. Therefore the system should expose configurable prize descriptions rather than inventing first-, second-, or third-place awards.

The requested prize categories are stage-progress assistance, ZP top-up cards with configurable denominations, help completing a pass by finding a team, and a possible special in-game or clan-related request subject to administrator approval. The public page must label these as competition prize categories and show availability only when the administrator publishes them.

## Administration

Administrators need a dashboard for competition configuration, invitation-code generation and revocation, question-bank CRUD, participant attempts, objective and essay scores, uploaded proof images, phone numbers, bonus approvals, leaderboard publication, and prize text. Each participant record should expose a safe WhatsApp contact action that uses the stored phone number and a configurable greeting template. The UI must not log or expose authentication secrets, service keys, or private proof URLs in public responses.

Administrative roles should be explicit. A super administrator may create or deactivate administrators and assign scoped access such as competition, content, sellers, or read-only. New administrator access must be protected by server-side authorization and must not be implemented as a client-only role selector.

## Contact and source verification

The prompt asks to retrieve contact links for Diaasadek, Antifarming, Zenith Clan, CrossFire Wiki’s WhatsApp channel, and Bemora’s YouTube channel. These links and phone numbers must be verified from the user’s supplied official sources or entered in the admin settings. The implementation must not guess or fabricate phone numbers, WhatsApp links, Discord invites, or prize details. Any unverified source should remain an editable placeholder with an explicit unverified state.

## Recommended implementation order

1. Repair Highlights, Announcements, and Admin Users through the existing authenticated admin API and improve error reporting.
2. Add a shared competition data model or JSON-backed configuration only after confirming the current Supabase schema and migration process. Prefer normalized tables for attempts, questions, proofs, codes, and administrator roles if the database is available.
3. Add one public bilingual competition route and one protected admin competition manager, reusing the existing auth, upload, route, and localization patterns.
4. Extract audio assets only when the storage and licensing path is confirmed; do not place large MP3 files in `client/public` or commit them into the Vite bundle.
5. Implement the objective quiz and result flow first, then proof upload, essay review, leaderboard, and WhatsApp contact actions.
6. Run TypeScript checks, production build, focused route tests, and RLS/auth regression tests. Keep the Vercel function count at or below 12.

## Open configuration required before production launch

The administrator must configure the official contact URLs, the phone number used for WhatsApp contact, the final scoring values, the exact purchase-age bonus policy, the published prize text, and the competition invitation-code policy. These values should be editable in the admin dashboard and should not be hard-coded as production facts.
